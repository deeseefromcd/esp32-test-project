# AGENTS.md — инструкции для AI-агентов

Этот файл описывает, что агент **обязан** делать после изменений в репозитории и на какие
грабли уже наступали. Читай его целиком перед работой; при сомнении — не догадывайся, а спроси.

---

## 1. Что это за репозиторий

Тестовый проект «мигающий светодиод» на **ESP32-S3** для симулятора [Wokwi](https://wokwi.com),
сборка через **PlatformIO**.

Ключевое разделение, которое нужно понимать (иначе половина инструкций ниже не имеет смысла):

| Сущность | Что делает | Обновляется автоматически? |
| --- | --- | --- |
| **Проект на wokwi.com** (`https://wokwi.com/projects/<id>`) | публичная страница-симулятор, которой делятся ссылкой | **Нет.** Только вручную (см. §2) |
| **Wokwi CI** (`.github/workflows/wokwi.yml`) | на каждый push собирает прошивку и гоняет её в облаке как тест | Да, по push/PR |
| **Прошивка в репозитории** (`src/main.cpp`) | исходник, который компилируется | — |

**Автосинхронизации «push в GitHub → проект на wokwi.com» не существует.**
Wokwi CI лишь проверяет код в облаке и не публикует ничего в профиль пользователя.

## 2. ОБЯЗАТЕЛЬНО после каждого пуша: обновить проект на wokwi.com

Целевой проект (он уже создан, пересоздавать не нужно):

- **URL:** <https://wokwi.com/projects/477978257402627073>
- **Название:** `ESP32-S3 Blink (LED on GPIO48)`
- **Видимость:** Public (чтобы ссылка работала у друзей без входа)

### Триггер

Ты запушил коммит в `main` (или в PR, который поменяет `main`) — значит, мог измениться
код (`src/main.cpp`), схема (`diagram.json`) или оба. Проверь `git diff` относительно предыдущего
сохранённого состояния. **Если `src/main.cpp` или `diagram.json` не менялись — синхронизация не нужна.**

### Предварительный шаг: убедиться, что агент вошёл в Wokwi

Браузерные инструменты OpenCode управляют **встроенным браузером Electron с отдельным профилем**.
Сессия из обычного Chrome/Safari туда не попадает.

1. Открой `https://wokwi.com/dashboard/projects`.
2. Если в тексте страницы есть `SIGN IN` — **ты не авторизован**. Логин (OAuth/email) должен
   выполнить пользователь. Скажи ему: «Войди в Wokwi в окне браузера OpenCode, потом скажи «вошёл»».
   Сам логин не выполняй и пароли не запрашивай.
3. Если видишь список проектов и имя пользователя — можно продолжать.

### Направление синхронизации

**Репозиторий — источник истины.** Всегда переноси файлы из репозитория на wokwi.com, а не
наоборот. Если содержимое проекта на wokwi.com разошлось с репозиторием (например, кто-то
подвигал детали в браузере) — приведи wokwi.com к состоянию репозитория и сообщи об этом.

### Процедура синхронизации

1. Навигация на `https://wokwi.com/projects/477978257402627073`.
2. Вставить код:
   - взять содержимое `src/main.cpp` **и** `sketch.ino` (они должны совпадать, см. §3);
   - через `browser.evaluate` записать в модель Monaco:
     ```js
     const model = monaco.editor.getModels().find(m => m.uri.toString() === 'vfs:sketch.ino');
     model.setValue(<JSON-строка с кодом>);
     ```
3. Вставить схему:
   - сначала **кликнуть** вкладку `diagram.json` (иначе модели `vfs:diagram.json` ещё нет);
   - затем записать в модель `vfs:diagram.json` содержимое файла `diagram.json` (через `JSON.stringify`).
4. **Проверить, что схема не сломалась:** открыть вкладку `Simulation`, нажать ▶ (Start),
   дождаться в serial строк `ESP32-S3 blink started (GPIO48)`, затем `LED ON` / `LED OFF`.
   Если строк нет — не сохраняй, сначала разберись (см. §4).
5. Остановить симуляцию.
6. Нажать **SAVE**.
   - Для **нового** проекта появится диалог «Save Your Project»: имя + выбор Public/Unlisted.
     Имя вводить **только** через `browser.fill` по ref из снапшота (см. §4.1), затем нажать
     SAVE в диалоге (это **последняя** кнопка SAVE в DOM).
   - Для **существующего** проекта SAVE сохраняет на месте; URL меняться не должен.
7. Проверить результат: URL остался `.../477978257402627073`, ошибок в консоли нет.

> **Важно:** перед перезагрузкой страницы сохрани проект — иначе `beforeunload`-диалог
> заблокирует навигацию (§4.3.1).

### Отчёт пользователю

Сообщи ссылку `https://wokwi.com/projects/477978257402627073` и что именно обновилось
(код / схема / оба). Не выдумывай, что «синхронизация прошла автоматически».

## 3. Обязательные проверки перед пушем

- **Окружение в порядке:** `make doctor` — «чего не хватает» и как это ставить (ничего не ставит).
  Ставит brew-зависимости `make setup`. Чего `make setup` не ставит (PlatformIO, `wokwi-cli`)
  и как их ставить — README, «Настройка с нуля».
- **Новый инструмент зарегистрирован в репозитории, а не только у тебя на диске.**
  Инструмент, ставящийся через brew, идёт строкой в `Brewfile` — `make setup` его
  поставит, а `make doctor` сам его подхватит (скрипт читает `Brewfile`). Не-brew
  инструмент (pio, wokwi-cli, node, openspec) объявляется в `scripts/doctor.sh`
  через `require`: имя, команда версии, команда установки. Инструмент, нужный
  **только в CI**, регистрируется в workflow, а не здесь.
- **`sketch.ino` и `src/main.cpp` должны быть синхронны.** `sketch.ino` — это ручная копия для
  вставки на wokwi.com; PlatformIO её не компилирует. Правишь одно — поправь второе (допустимо
  оставить в `.ino` шапку-комментарий, но тело кода должно совпадать).
- **`make check` проходит** — это lint (cppcheck + схема + `config.yaml` + workflow) и сборка.
  Для правки только документации достаточно `make lint`.
- Не пушь, пока не понял, *почему* проходят или падают тесты.

## 4. Известные проблемы и обходные пути

Это не теория, а то, на что реально наступали. Применяй обходы сразу, не переоткрывай заново.

### 4.1 React-поля не принимают значение через `element.value = ...`

В модалке «Save Your Project» прямое присваивание:
```js
input.value = 'Имя';
input.dispatchEvent(new Event('input', { bubbles: true }));
```
**не работает** — React сбрасывает значение, кнопка SAVE остаётся неактивной.

**Обход:** `browser.snapshot` → взять ref поля → `browser.fill({ ref, text })`. Это настоящий ввод,
React его видит. Затем кликнуть SAVE **по ref** (не через `element.click()`).

### 4.2 `browser.screenshot` требует видимой вкладки

Ошибка `Screenshot needs a visible tab`. **Обход:** сначала `browser.tabs.focus({ tabID })`,
затем скриншот. Вкладка должна быть видимой (окно OpenCode не свёрнуто).

### 4.3 Модель `vfs:diagram.json` появляется только после клика по вкладке

`monaco.editor.getModels()` содержит модели **только открытых** вкладок. Пока вкладка `diagram.json`
не активна, `vfs:diagram.json` в списке нет (и наоборот — нет `vfs:sketch.ino`, пока активна
`diagram.json`). Пустой список моделей сразу после загрузки — нормально.

**Обход:** сначала `browser.click` по кнопке нужной вкладки, затем искать модель. Если модель
не нашлась — перекинь вкладку и попробуй снова, но не записывай `setValue` на `undefined`.

### 4.3.1 `browser.reload` при несохранённых изменениях открывает JS-диалог

Wokwi ставит `beforeunload`. Если есть несохранённые правки, `reload`/`navigate` падает с
`A JavaScript dialog opened...`.

**Обход:** `browser.dialog({ tabID, action: "accept" })` — и не повторяй исходную навигацию
только чтобы закрыть диалог. Сначала **сохрани** проект, потом перезагружай.

### 4.3.2 Проверка, что данные реально на сервере (а не только в редакторе)

`setValue` меняет только модель в памяти. Чтобы убедиться, что состояние сохранено:

1. Нажать **SAVE**.
2. Открыть проект в **новой** вкладке (`browser.tabs.open`) — она загружает данные с сервера.
3. Фоновая вкладка не рендерится (`monaco is not defined`, пустой `body`). Нужен
   `browser.tabs.focus` на новой вкладке и ожидание `condition: "text", text: "sketch.ino"`.
4. Сравнить содержимое моделей с файлами репозитория.

Без этого шага легко решить, что «сохранилось», хотя на сервере старые данные.

### 4.4 Serial-монитор на ESP32-S3 подключается только явными проводами

Без строк ниже в `diagram.json` симуляция даёт **пустой serial**, и Wokwi CI падает по таймауту:
```json
[ "esp:TX", "$serialMonitor:RX", "", [] ],
[ "esp:RX", "$serialMonitor:TX", "", [] ]
```
**Не удаляй их.** Это была причина падения CI (коммит `e8c4bf9`).

### 4.5 Ошибки окружения Code Mode

- В `browser.evaluate` **нет** `setTimeout`, `require`, `process`.
- Для ожидания используй `browser.wait` (`condition: "load" | "text" | "textGone"`).
- `browser.snapshot` принимает `depth` **от 1 до 20**.

### 4.6 Сломанный `pio` из brew (только эта macOS-машина)

`brew install platformio` тянет Python 3.15, где `platform.mac_ver()` возвращает `''` → падение
`pip` на `tool-esptoolpy` → `MissingPackageManifestError`.

**Обход:** отдельное venv (`~/.platformio-venv/bin/pio`). Makefile находит его автоматически
(иначе берёт `pio` из PATH), так что жёстких машинных путей в командах нет.
Проверить окружение: `make doctor`; поставить brew-зависимости: `make setup`.

**Важно при правке Makefile:** пути `PIO` и `WOKWI_CLI` определяются через автодетект
(`ifeq ($(strip $(PIO)),)` + `$(shell ...)`). Не заменяй их обратно на хардкод
`$(HOME)/.platformio-venv/...` — на машине коллеги без этого venv команда сломается.

### 4.7 Wokwi CI ≠ страница wokwi.com

Не пытайся «залить» что-то на wokwi.com из GitHub Action — такого API нет. CI только прогоняет тест.

### 4.8 Позиции деталей на схеме

`wokwi-led` и `wokwi-resistor` на широком полотне могут оказаться за краем видимой области —
это косметика, соединения при этом рабочие. Проверяй именно **запуском** симуляции, а не глазами.

### 4.9 Юнит-тесты: пока нет, и почему

В проекте намеренно нет юнит-тестов, и это решение, а не недоделка.

**Причина.** Весь код — побочные эффекты против железа (`digitalWrite`, `delay`, `Serial`),
чистой логики нет, изолировать нечего.

**Не заводи `pio test` для среды `esp32-s3-devkitc-1` с моками Arduino.** Проверено:
тестовая прошивка собирается, но прогон падает на загрузке —
`*** [upload] Error 2`, `0 succeeded` — нужна плата. Это та же ошибка, что была с
`blink.test.yaml` в цикле: **цель, невыполнимая локально**. Ставить её в `make check`
нельзя.

**Порог, с которого тесты появляются.** Как только от «дёргаю пин» возникает чистая
логика (паттерн мигания, разбор строки из serial, автомат состояний, антидребезг) —
она выносится в `src/` **отдельным модулем без `Arduino.h`** (на входе/выходе числа
или структуры), и только тогда добавляется:

1. `[env:native]` (`platform = native`) в `platformio.ini`;
2. каталог `test/` с тестами;
3. цель `make test` → `pio test -e native`.

Native-тесты идут **на хосте, без платы и без токена**, поэтому это единственный
вариант юнит-тестов, который здесь реально запускается.

**Что тестировать не надо.** Проверку поведения прошивки (serial, уровень пина)
делает `blink.test.yaml` в Wokwi CI. Юнит-тест этого не заменяет и не дублирует.

### 4.10 Токен Wokwi CI — это секрет

`WOKWI_CLI_TOKEN` живёт только в GitHub Secrets. Не запрашивай его у пользователя, не логируй,
не коммить.

## 4A. Работа через OpenSpec (SDD)

Проект использует [OpenSpec](https://openspec.dev). Правила работы — в
`docs/SDD-WORKFLOW.md`; читай его, если задача меняет наблюдаемое поведение.

**Триггер:** задача меняет поведение, публичный контракт или схему симуляции — сначала
планирование, потом код. Опечатка, рефакторинг без изменения поведения, обновление
зависимости — обычный коммит, OpenSpec не нужен.

**Planning boundary.** Пока идёт планирование, код не трогается. Если пользователь вызвал
`/opsx-propose`, создавай только артефакты и остановись; реализация — отдельным запросом
(`/opsx-apply`).

### Ключевые правила формата

Валидатор OpenSpec разбирает файлы по разметке. Если разметка не та — артефакт молча
считается некорректным, и это трудно заметить на глаз.

- **Структурные заголовки только по-английски:** `## Why`, `## What Changes`,
  `### Requirement:`, `## ADDED Requirements`. Русский текст — в теле, но не в этих заголовках.
  Проект настроен на `--language ru` (см. `openspec/config.yaml`).
- **Сценарии — ровно четыре решётки:** `#### Scenario:`. С `###` или списком сценарий
  не распознаётся **без ошибки**.
- **`SHALL`/`MUST`** для нормативных требований (не «должно бы»).
- **Описание требования короче 500 символов.** Иначе `--strict` ругается. Примеры и
  крайние случаи — в сценарии, а не в описании.
- **У каждого требования есть хотя бы один сценарий.**
- **У каждой задачи в `tasks.md` есть способ проверки** — в тексте самой задачи.
- **Чекбокс считается выполненным только с `x`** внутри (`- [x]`). `- [~]`, `- [-]`,
  `- []` — не выполнено.

### Обязательные команды

```sh
# CLI не установлен глобально — вызывай через npx
npx @fission-ai/openspec@latest validate <change> --strict   # ПЕРЕД тем как считать работу готовой
npx @fission-ai/openspec@latest status --change <change>
npx @fission-ai/openspec@latest list --specs                 # способности проекта
```

`validate --strict` должен проходить. Не отчитывайся о готовности изменения, пока он падает.

### Цикл реализации (apply)

Порядок проверок **не дублируется в этом файле** — он лежит в `openspec/config.yaml`
в `operations.apply.guidance`, и CLI отдаёт его тебе при `/opsx-apply`. Не забудь прочитать
этот блок перед реализацией:

```sh
npx @fission-ai/openspec@latest instructions apply --change <change> --json
```

В ответе смотри поля `context` (обязательные вводные проекта) и `operationGuidance`
(какие проверки прогнать после каждой правки). Если меняешь проект, где этих проверок
не хватает, — правь `config.yaml`, а не добавляй правила локально в сессию.

Задачу отмечай `- [x]` **только** после того, как её проверка прошла.

### Что проверяется где

| Проверка | Команда | Локально | В CI |
| --- | --- | --- | --- |
| Дефекты C++ | `make lint-cppcheck` (cppcheck) | да | — |
| Схема `diagram.json` | `make lint-diagram` | да | — |
| `openspec/config.yaml` | `make lint-yaml` | да | — |
| Workflow | `make lint-workflow` (actionlint) | да | — |
| Сборка | `make build` | да | да |
| **Поведение (serial + пин)** | `blink.test.yaml` | **нет** | да |
| **Юнит-тесты** | `pio test -e native` | пока нет цели | — |
| **Окружение** | `make doctor` | да | — |

Всё локальное сразу — `make lint`; локальное плюс сборка — `make check`.

**`blink.test.yaml` локально прогнать нельзя** — `wokwi-cli` требует `WOKWI_CLI_TOKEN`,
а он живёт только в GitHub Secrets. Не обещай пользователю, что прогнал сценарий на машине:
поведение проверяется Wokwi CI по push либо симуляцией в браузере (AGENTS.md, раздел 2).

### Грабли

- **Строка с `": "` в `config.yaml` обязана быть в кавычках.** Иначе YAML прочитает её как
  mapping, и OpenSpec **молча отбросит** все правила артефакта или всю секцию guidance.
  Ловит `make lint-yaml` (`scripts/check-openspec-config.rb`); `openspec validate` этот
  дефект пропускает.
- **Не создавай `openspec/` руками** и не запускай `init` без просьбы — структура уже есть.
- **Не правь `openspec/specs/` напрямую во время работы** — главные спеки обновляются
  при архивации из дельты изменения.
- **`MODIFIED Requirements` копируется целиком** — от `### Requirement:` со всеми
  сценариями. Частичная копия при архивации потеряет детали.
- **Нулевая дельта запрещена**: изменение без capability требует `skip_specs: true`
  в его `.openspec.yaml`, иначе `validate` падает. Не выдумывай требование ради галочки.
- **Изменение схемы симуляции — двойная работа:** после архивации не забудь синхронизацию
  с wokwi.com (§2).

## 5. Границы

- Не выполняй логин на сторонних сервисах за пользователя и не запрашивай пароли.
- Не сохраняй проект на wokwi.com, если симуляция не проверена (§2 шаг 4).
- Не меняй видимость существующего проекта на wokwi.com (сейчас — Public).
- Не начинай реализацию в том же ответе, что и планирование OpenSpec (§4A).
- Если инструкция устарела (например, проект переименован или получил новый id) —
  обнови этот файл и README, а не действуй вслепую.
