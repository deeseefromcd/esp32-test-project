# Разработка через спецификации (SDD) с OpenSpec

Этот проект использует [OpenSpec](https://openspec.dev) — лёгкий слой спецификаций,
который заставляет человека и AI-агента **сначала договориться о том, что строить**,
и только потом писать код.

Работает просто: договорённость живёт в Markdown-файлах внутри репозитория, а не в
истории чата. Агент пишет черновик, ты его правишь и утверждаешь, и лишь затем начинается
реализация.

---

## 1. Что уже настроено

`openspec init` создал в репозитории:

```
openspec/
├── config.yaml              # конфигурация: схема spec-driven + правила проекта
├── specs/                   # ГЛАВНЫЕ спеки (что система умеет сейчас) — источник истины
└── changes/                 # предлагаемые изменения
    ├── fix-wokwi-ci-serial-monitor/   # пример: разбор прошлой задачи (см. §7)
    └── archive/             # завершённые изменения

.opencode/
├── commands/opsx-*.md       # слэш-команды для OpenCode
└── skills/openspec-*/       # навыки, которые использует агент
```

Ключевое разделение:

| Папка | Что это | Когда меняется |
| --- | --- | --- |
| `openspec/specs/` | **что система делает сейчас** — актуальное поведение | при архивации изменения |
| `openspec/changes/<имя>/` | **что мы предлагаем изменить** — черновик | во время работы над задачей |

Спека описывает **поведение**, а не код. Тест на границу: если реализацию можно
переписать, а видимое поведение не изменится — это не в спеку, это в `design.md` или `tasks.md`.

## 2. Рабочий цикл

```
/opsx-propose  →  (обзор и правки)  →  /opsx-apply  →  /opsx-archive
   черновик          договорились        реализация      спеки обновились
```

| Команда | Что делает |
| --- | --- |
| `/opsx-explore` | Подумать вслух без обязательств: читает код, взвешивает варианты, предлагает план |
| `/opsx-propose <что сделать>` | Создаёт каталог изменения и генерирует все артефакты: `proposal.md`, `specs/`, `design.md`, `tasks.md` |
| `/opsx-update` | Поправить артефакты по ходу — без жёстких фаз |
| `/opsx-sync` | Перенести дельту спек в главные спеки, не архивируя изменение |
| `/opsx-apply` | Реализовать `tasks.md`, отмечая выполненные пункты |
| `/opsx-archive` | Проверить, влить дельту в `openspec/specs/` и убрать изменение в `archive/` |

Есть ещё профиль с командами `new`, `continue`, `ff`, `bulk-archive`, `verify`, `onboard`.
Добавить: `openspec config profile`.

### Четыре артефакта

| Артефакт | Отвечает на вопрос | Обязателен |
| --- | --- | --- |
| `proposal.md` | **Зачем** и **что** меняется, какие capability затронуты | да |
| `specs/<capability>/spec.md` | **Какое поведение** требуется (дельты: ADDED/MODIFIED/REMOVED) | да, пока не `skip_specs: true` |
| `design.md` | **Как** реализовать, какие компромиссы | только если есть нетривиальные решения |
| `tasks.md` | **Пошаговый план** с чекбоксами и способом проверки | да |

### Правила, которые важнее всего

1. **Planning boundary.** `/opsx-propose` пишет только документы и не трогает код.
   Реализация начинается отдельной командой `/opsx-apply`. Это защищает от «агент сразу
   накодил не то».
2. **Сценарии строго с четырьмя решётками.** `#### Scenario:` — именно `####`.
   С тремя решётками или списком сценарий молча не распознаётся.
3. **SHALL/MUST для требований.** Не «should» и не «может».
4. **Одно требование — одно поведение.** Описание требования короче 500 символов,
   иначе `--strict` ругается. Примеры и крайние случаи — в сценарии.
5. **У каждой задачи есть способ проверки** прямо в её тексте (тест, команда,
   наблюдаемое поведение).
6. **Проверяй себя валидатором:** `openspec validate <имя> --strict`.

## 3. Настройка процесса: `openspec/config.yaml`

Ключевой момент: **инструкции по реализации не нужно писать отдельным файлом для агента.**
OpenSpec сам читает `openspec/config.yaml` и подставляет его содержимое агенту. Проверено:

```sh
npx @fission-ai/openspec@latest instructions apply --change <имя> --json
```

возвращает поля `context` (обязательный ввод) и `operationGuidance` (советы для apply).

| Секция | Куда попадает | Для чего |
| --- | --- | --- |
| `context` | в инструкции **каждого** артефакта, apply и archive | команды проекта, контракт, ограничения процесса |
| `rules.<артефакт>` | в инструкции конкретного артефакта (`proposal`, `specs`, `design`, `tasks`) | правила оформления именно этого документа |
| `operations.apply.guidance` | в `operationGuidance` при apply | **цикл реализации**: что проверить после каждой правки |
| `operations.archive.guidance` | при архивации | что показать/проверить перед архивацией |

Именно в `operations.apply.guidance` и описан цикл «код → проверка». В нашем проекте он такой:

```yaml
operations:
  apply:
    guidance:
      - "Быстрая локальная проверка после правок: make check (cppcheck + схема + config.yaml + workflow + сборка)."
      - "Правка только документации или OpenSpec-артефактов: make check избыточен, достаточно make lint."
      - "Перед отчётом о готовности: npx @fission-ai/openspec@latest validate <change> --strict должен проходить."
      - "Проверку поведения (blink.test.yaml) локально прогнать НЕЛЬЗЯ: нужен WOKWI_CLI_TOKEN, он есть только в GitHub Secrets."
      - "Проверка поведения прошивки — это blink.test.yaml в CI, а не юнит-тесты. Юнит-тест добавляй ТОЛЬКО если появилась чистая логика, вынесенная в src/ без Arduino.h, и тогда он идёт на [env:native]."
```

Ключевой момент — **все команды собраны за двумя целями `make`**, а не расписаны по одной.
Это не стилистика: если перечислять шаги по отдельности в трёх местах (`config.yaml`,
`AGENTS.md`, `Makefile`), они разъедутся. Так уже почти случилось: в первой версии этого
цикла стоял шаг «прогони `blink.test.yaml`», который **локально невыполним** — токена нет.

> **Нельзя проверить локально, не пиши в цикл.** Любой шаг, который агент физически не может
> прогнать на машине, выглядит как выполненная проверка, хотя ею не является. Признак этой
> ошибки: `wokwi-cli` требует `WOKWI_CLI_TOKEN`, а он есть только в CI.

Больше нигде это дублировать не нужно — ни в `AGENTS.md`, ни в шаблоне `tasks.md`.
Так цикл проверок остаётся в одном месте и автоматически доезжает до агента.
В `AGENTS.md` лежит только таблица «что проверяется где».

> **Грабли YAML.** Строку с `": "` внутри **обязательно** бери в кавычки. Без кавычек YAML
> прочитает её как `ключ: значение`, и OpenSpec **молча отбросит все** правила артефакта
> или всю секцию guidance. Выглядит это так:
>
> ```
> Rules for 'specs' must be an array of strings, ignoring this artifact's rules.
> Guidance for operation 'archive' must be an array of strings, ignoring this operation's guidance
> ```
>
> **`openspec validate` этот дефект пропускает** — он проверяет изменения, а не конфиг.
> Ловится через `make lint-yaml` (`scripts/check-openspec-config.rb`).
>
> Проверка, что конфиг прочитан: в выводе `instructions apply --json` должны быть
> заполнены `context` и `operationGuidance`.

## 4. Язык артефактов

В `openspec/config.yaml` зафиксировано:

```yaml
context: |
  Language: ru
  All artifacts must be written in ru.
  Keep OpenSpec structural headings and SHALL/MUST keywords in English.
```

Читаем так: **текст по-русски, а структурные заголовки — по-английски**. Писать
`## Почему` вместо `## Why` или `### Требование:` вместо `### Requirement:` нельзя —
парсер OpenSpec их не увидит, и валидация провалится. Слова `SHALL`/`MUST` тоже
остаются английскими.

## 5. Как это работает на практике: агент или руками

Короткий ответ: **каталог и артефакты создаёт агент, а ты читаешь и правишь.**

Тебе не нужно создавать файлы «по аналогии» и копировать шаблоны. Достаточно одной фразы:

```
/opsx-propose Добавить кнопку, которая останавливает мигание
```

Агент (по навыку `openspec-propose`) сам:
1. выведет kebab-case имя изменения;
2. выполнит `openspec new change <имя>`;
3. сгенерирует `proposal.md`, дельты в `specs/`, при необходимости `design.md` и `tasks.md`;
4. остановится — **код не тронет** (planning boundary).

Дальше твоя роль — прочитать и возразить, пока это дёшево. Правки вноси так же словами:
«в сценарии добавь случай, когда кнопка уже нажата» — агент перепишет нужный файл
(это делает `/opsx-update`).

Шаблоны из этого раздела нужны в трёх случаях:

- **проверить агента** — сверить, что структура правильная;
- **поправить мелкое вручную** — одну строку быстрее исправить самому, чем формулировать запрос;
- **понять формат** — чтобы читать артефакты и знать, что именно ломает валидатор.

Чего делать **не** надо:

- не копируй шаблон вручную, когда есть CLI — потеряешь `.openspec.yaml` и дату в имени;
- не создавай `openspec/` или `specs/` руками (структура уже есть);
- не правь `openspec/specs/` напрямую во время работы над изменением — главные спеки
  обновляются при архивации.

## 6. Шаблоны

Файлы создаёт CLI, но вот пустые скелеты — чтобы понимать структуру и уметь править руками.

### `proposal.md`

```markdown
# Proposal

## Why

<!-- Проблема или возможность. Почему именно сейчас. Смотри в корень, не описывай реализацию. -->

## What Changes

<!-- Что конкретно меняется: новое, изменённое, удалённое. Ломающее — помечай **BREAKING**. -->

## Capabilities

### New Capabilities

<!-- Новые способности системы. Каждая станет specs/<capability-path>/spec.md.
     Имя = устойчивое поведение (wokwi-simulation), а не задача (fix-serial-monitor).
     kebab-case. Одна способность = одна связная область ответственности. -->
- `<capability-path>`: чем эта способность управляет

### Modified Capabilities

<!-- Существующие способности, у которых меняются ТРЕБОВАНИЯ (не реализация).
     Точный существующий путь под openspec/specs/. Если требований не меняется — оставь пусто. -->
- `<existing-capability-path>`: какое требование меняется

## Impact

<!-- Затронутый код, интерфейсы, зависимости, системы. Публичные контракты. -->
```

### `specs/<capability>/spec.md` — дельта спеки

```markdown
# Spec Delta

## Purpose

<!-- Только для НОВОЙ способности: 1–2 предложения (от 50 символов), зачем она нужна.
     Для существующей способности эту секцию удали. -->

## ADDED Requirements

### Requirement: <!-- имя требования, одно предложение, короче 500 символов -->
<!-- Описание поведения. Используй SHALL/MUST. -->

#### Scenario: <!-- имя сценария -->
- **WHEN** <!-- условие -->
- **THEN** <!-- ожидаемый результат -->

## MODIFIED Requirements

<!-- Копируй ЦЕЛИКОМ существующее требование (от ### Requirement: со всеми сценариями)
     и правь. Частичная копия молча потеряет детали. -->

## REMOVED Requirements

### Requirement: <!-- имя -->
**Reason**: <!-- почему убираем -->
**Migration**: <!-- что делать вместо -->
```

### `design.md`

```markdown
# Design

## Context

<!-- Текущее состояние и ограничения. Мотивацию не повторяй — см. proposal.md. -->

## Goals / Non-Goals

**Goals:**
<!-- Что этот дизайн должен дать -->

**Non-Goals:**
<!-- Что явно вне рамок -->

## Decisions

<!-- Ключевые решения: почему X, а не Y. Альтернативы и причина отказа. -->

## Risks / Trade-offs

<!-- [Риск] → как снижаем -->
```

### `tasks.md`

```markdown
# Tasks

## 1. <!-- Группа задач -->

- [ ] 1.1 <!-- Задача + как проверить: тест, команда, наблюдаемое поведение -->

## 2. <!-- Группа задач -->

- [ ] 2.1 <!-- Задача + как проверить -->

## Workflow follow-up

<!-- Необязательно: шаги вне чекбоксов (архивация и т.п.) -->
```

> Чекбокс засчитывается как выполненный только при `x` внутри (`- [x]`, регистр и
> пробелы не важны). `- [~]`, `- [-]`, `- []` считаются незавершёнными.

## 7. Разбор прошлой задачи

Возьмём реальный случай: **Wokwi CI падал на шаге `Test with Wokwi`**. Тогда мы шли без
SDD — вот как та же задача выглядела бы через OpenSpec.

Готовый пример лежит в `openspec/changes/fix-wokwi-ci-serial-monitor/`.
Проверить: `npx @fission-ai/openspec@latest validate fix-wokwi-ci-serial-monitor --strict`.

### Шаг 1. Команда

```
/opsx-propose Починить падение Wokwi CI: симуляция подключается, но serial пуст
```

Агент предлагает имя `fix-wokwi-ci-serial-monitor` и создаёт черновики. Правки в код
**не вносятся** — это planning boundary.

### Шаг 2. `proposal.md` — зачем

Ключевое здесь — **Capabilities**. Это мост к спекам: что перечислишь, для того и
потребуются дельта-файлы. В нашем случае:

- `wokwi-simulation` — контракт схемы: какие соединения обязаны быть, чтобы вывод был наблюдаем;
- `ci-verification` — контракт пайплайна: что проверяется и когда прогон падает.

Обрати внимание: способности названы **устойчиво** (`wokwi-simulation`), а не по имени
задачи (`fix-ci`). Завтра появится другая правка схемы — она ляжет в ту же способность.

### Шаг 3. `specs/` — что должно быть

Здесь фиксируется наблюдаемое поведение, без деталей реализации:

```markdown
### Requirement: Serial-монитор подключён к плате
Схема SHALL соединять serial-монитор с платой: `esp:TX` → `$serialMonitor:RX`
и `esp:RX` → `$serialMonitor:TX`. У платы ESP32-S3 автоматического подключения нет,
поэтому соединения задаются явно.

#### Scenario: Вывод прошивки транслируется в монитор
- **WHEN** симуляция запускается со схемой проекта
- **THEN** serial-монитор получает строки, которые печатает прошивка
```

Почему это спека, а не задача: **наблюдаемое поведение**, которое переживёт реализацию.
Если завтра Wokwi научит ESP32-S3 подключаться сам, требование не изменится — изменится
только способ его выполнения.

### Шаг 4. `design.md` — как

Тут то, что в спеку не влезает: **выбор из альтернатив**. В примере зафиксировано
решение — явные соединения `esp:TX`/`esp:RX`, а не перевод на USB CDC
(`serialInterface: USB_SERIAL_JTAG`), с причиной отказа. Через полгода никто не будет
гадать, почему сделано именно так.

### Шаг 5. `tasks.md` — план

Задачи сгруппированы по зависимостям, и у каждой — способ проверки в самом тексте:

```markdown
- [x] 2.1 Добавить в `diagram.json` соединения `esp:TX` → `$serialMonitor:RX` и `esp:RX` → `$serialMonitor:TX` и проверить, что `wokwi-cli lint` проходит.
```

### Шаг 6. Проверка и реализация

```sh
openspec validate fix-wokwi-ci-serial-monitor --strict   # документы корректны
/opsx-apply                                              # реализовать задачи
```

### Шаг 7. Архивация

```
/opsx-archive
```

Дельта из `specs/wokwi-simulation/spec.md` вливается в
`openspec/specs/wokwi-simulation/spec.md` — это и есть актуальная спека проекта.
Сам каталог изменения уезжает в `archive/` с датой. С этого момента требование
про serial-монитор проверяется валидатором уже как часть основной спеки.

### Что бы это дало

| Без SDD | С SDD |
| --- | --- |
| Причина падения CI искалась заново | Зафиксирована в `design.md` с альтернативами |
| Знание про TX/RX жило в `AGENTS.md` прозой | Стало требованием со сценариями, которое проверяет валидатор |
| Непонятно, что уже сделано | `tasks.md` с чекбоксами и проверками |
| «А почему не USB CDC?» — неизвестно | Решение и причина отказа задокументированы |

## 8. Шпаргалка

```sh
# Инициализация (уже сделана)
npx @fission-ai/openspec@latest init --tools opencode --language ru

# Посмотреть состояние
npx @fission-ai/openspec@latest list            # активные изменения
npx @fission-ai/openspec@latest list --specs    # способности проекта
npx @fission-ai/openspec@latest view            # интерактивный дашборд
npx @fission-ai/openspec@latest status --change <имя>
npx @fission-ai/openspec@latest show <имя>

# Проверка
npx @fission-ai/openspec@latest validate <имя> --strict
npx @fission-ai/openspec@latest validate --all --strict

# Создать изменение вручную
npx @fission-ai/openspec@latest new change <имя>
```

В OpenCode то же самое доступно слэш-командами: `/opsx-explore`, `/opsx-propose`,
`/opsx-apply`, `/opsx-sync`, `/opsx-update`, `/opsx-archive`.

> Отключить телеметрию: `openspec config set telemetry.enabled false`
> или `export OPENSPEC_TELEMETRY=0`.

## 9. Проверки: что где запускается

Все локальные проверки собраны за двумя целями `make`:

```sh
make lint    # cppcheck + схема + config.yaml + workflow   (~10 секунд)
make check   # lint + сборка прошивки
```

| Проверка | Команда | Локально | В CI |
| --- | --- | --- | --- |
| Дефекты C++ | `make lint-cppcheck` (cppcheck) | да | — |
| Схема `diagram.json` | `make lint-diagram` (`wokwi-cli lint`) | да | — |
| `openspec/config.yaml` | `make lint-yaml` | да | — |
| Workflow | `make lint-workflow` (actionlint) | да | да |
| Сборка | `make build` | да | да |
| **Поведение (serial + пин)** | `blink.test.yaml` | **нет** | да |
| **Юнит-тесты** | `pio test -e native` | пока нет цели | — |

### Почему поведение проверяется только в CI

`wokwi-cli` требует `WOKWI_CLI_TOKEN`, а он лежит в GitHub Secrets и намеренно не хранится
локально. Поэтому локально доступны сборка, схема, cppcheck и статические проверки, а
**поведение** проверяет Wokwi CI по push либо симуляция в браузере.

Это важно понимать при работе через SDD: если задача меняет поведение, её нельзя закрыть
только по зелёному `make check` — нужен прогон CI или проверка в браузере. Не отмечай
задачу `- [x]`, если проверка её поведения не выполнена.

### Про порог cppcheck

`make lint-cppcheck` использует `--fail-on-defect medium`. На Arduino-скетчах cppcheck даёт
ложные срабатывания уровня `low`:

```
src/main.cpp:17: [low:style] The function 'setup' is never used. [unusedFunction]
src/main.cpp:23: [low:style] The function 'loop' is never used. [unusedFunction]
```

`setup` и `loop` вызывает фреймворк Arduino — это не дефект. Порог `medium` отсекает шум,
оставляя настоящие проблемы. Если понизить порог до `low`, `make lint` начнёт падать на
корректном коде.

### Юнит-тесты: почему их нет и когда появятся

Сейчас в проекте **намеренно нет** `pio test` — и это решение, а не пробел.

Весь код прошивки — побочные эффекты против железа: `digitalWrite`, `delay`, `Serial`.
Чистой логики, которую можно изолировать от железа, в нём нет, поэтому юнит-тест
проверял бы моки (`digitalWrite` «был вызван»), а не поведение.

**Локально `pio test` не запускается.** Проверено на пробном тесте:

```
$ pio test -e esp32-s3-devkitc-1
Library Manager: Unity@2.6.1 has been installed!
*** [upload] Error 2
esp32-s3-devkitc-1  test_blink  ERRORED
================== 1 test cases: 0 succeeded ==================
```

Тестовая прошивка **собирается**, но падает на загрузке: нужна плата. `--without-uploading`
даёт `[SKIPPED]` и `0 test cases`. Это ровно та же ловушка, что была с `blink.test.yaml` в
цикле apply: цель, невыполнимая на машине, выглядит как пройденная проверка, но ею не
является. Поэтому её здесь и не заводят.

#### Порог: когда юнит-тесты появляются

Признак один — **появилась чистая логика, отделяемая от железа**:

- паттерн мигания (последовательность фаз и длительностей);
- разбор строки команды из serial;
- автомат состояний;
- антидребезг кнопки.

Тогда порядок такой:

1. Вынести логику в `src/` **отдельным модулем без `Arduino.h`** — на входе и выходе
   числа или структуры, никаких обращений к железу.
2. Добавить `[env:native]` (`platform = native`) в `platformio.ini`.
3. Положить тесты в `test/` и добавить цель `make test` → `pio test -e native`.

Native-тесты исполняются **на хосте, без платы и без токена** — это единственная форма
юнит-тестов, которая здесь запускается локально. Пока такой логики нет, шаги 1–3
преждевременны.

#### Что юнит-тесты не заменяют

Поведение прошивки в железе (serial, уровень пина) проверяет `blink.test.yaml` в Wokwi CI.
Юнит-тест этого не дублирует и не заменяет — как и наоборот.

Показательно, что **оба реальных бага этого репозитория** нашли не линтеры и не могли бы
найти юнит-тесты: пустой serial поймал `blink.test.yaml`, кривой YAML в `config.yaml` —
скрипт-проверка.

## 10. Когда SDD избыточен

Не заводи изменение под каждую мелочь:

- опечатка, переименование переменной, обновление зависимости — просто коммит;
- правка, которая ничего не меняет в наблюдаемом поведении, — `skip_specs: true`
  в `.openspec.yaml` изменения (иначе `validate` откажется принимать нулевую дельту);
- а вот всё, что меняет **наблюдаемое поведение**, **публичный контракт** или
  **схему симуляции**, — сюда, в изменение.

Помни про `AGENTS.md`: изменение `src/main.cpp` или `diagram.json` требует ещё и
синхронизации проекта на wokwi.com.
